# КТ-4. Ответы на вопросы

## Java Core

**1. Статическое и динамическое связывание**
Статическое - на этапе компиляции по типу ссылки (private, static, final методы, перегрузка, поля). Динамическое - во время выполнения по реальному типу объекта (переопределённые методы, полиморфизм).

**2. private/protected переменные в interface**
Нельзя. Все поля интерфейса неявно public static final. С Java 9 разрешены private методы, protected - никогда.

**3. ClassLoader**
Компонент JVM, который загружает классы в память во время выполнения. Иерархия: Bootstrap -> Platform -> Application, работает делегирование родителю. Свои загрузчики используют для изоляции приложений (Tomcat), плагинов, горячей перезагрузки.

**4. Run-Time Data Areas**
Области памяти JVM. Общие: Heap, Method Area (Metaspace), Run-Time Constant Pool. У каждого потока свои: PC Register, JVM Stack, Native Method Stack.

**5. Immutable object**
Объект, состояние которого нельзя изменить после создания (String, Integer, LocalDate). Делается так: final класс, private final поля, нет сеттеров, защитные копии изменяемых полей.

**6. Особенности String**
Неизменяемый и final, литералы хранятся в String Pool, сравнивать через equals(), хеш-код кэшируется, потокобезопасен.

**7. Ковариантность типов**
Если B подтип A, то контейнер B считается подтипом контейнера A. Массивы ковариантны (String[] это Object[]), generics инвариантны, ковариантность задаётся через `? extends`. Также ковариантные возвращаемые типы при переопределении.

**8. Методы Object**
equals, hashCode, toString, getClass, clone, finalize (устарел), wait (3 варианта), notify, notifyAll.

**9. Optional: удачно и неудачно**
Удачно - как возвращаемый тип метода, который может ничего не найти:
```java
User user = repository.findById(id).orElseThrow(() -> new UserNotFoundException(id));
String name = repository.findByEmail(email).map(User::getName).orElse("Гость");
```
Неудачно - в полях и параметрах, для коллекций (лучше пустой список), `get()` без проверки, присваивание Optional значения null.

**10. main как final**
Можно, программа запустится как обычно.

**11. Повторный импорт**
Можно, компилятор игнорирует повтор, последствий нет. Ошибка будет только при импорте двух разных классов с одинаковым именем (java.util.Date и java.sql.Date).

**12. Casting и ClassCastException**
Casting - приведение типа. Upcasting к родителю автоматический, downcasting к наследнику явный. ClassCastException возникает при downcasting, если объект на самом деле не того типа. Защита - проверка instanceof.

**13. Почему фреймворки используют unchecked exceptions**
Checked засоряют сигнатуры всех слоёв, ломают инкапсуляцию, плохо работают с лямбдами, а обработать их на промежуточных слоях обычно нельзя. Unchecked удобно обрабатывать централизованно, и Spring откатывает транзакцию именно на них.

**14. Static import**
Позволяет использовать статические члены класса без имени класса: `import static java.lang.Math.sqrt;`.

**15. Связь hashCode() и equals()**
Если объекты равны по equals(), их hashCode() обязан совпадать (обратное не обязательно). Переопределяются вместе, иначе HashMap и HashSet работают неправильно.

**16. BufferedInputStream и BufferedOutputStream**
Когда много мелких операций чтения/записи файла или сокета: буфер уменьшает число обращений к диску и сети.

**17. Collection и Collections**
Collection - корневой интерфейс коллекций. Collections - утилитный класс со статическими методами (sort, reverse, unmodifiableList и др.).

**18. Enumeration и Iterator**
Enumeration - устаревший, только чтение. Iterator - новее, умеет удалять элементы (remove) и в большинстве коллекций fail-fast.

**19. Fail-fast и fail-safe**
Fail-fast бросает ConcurrentModificationException, если коллекцию изменили во время обхода (ArrayList, HashMap). Fail-safe обходит копию или конкурентную структуру и исключение не бросает (CopyOnWriteArrayList, ConcurrentHashMap).

**20. transient**
Поле с transient не сериализуется (пароли, кэши, несериализуемые объекты). После десериализации у него значение по умолчанию.

**21. static и final при сериализации**
static поля не сериализуются. final сериализуются как обычные. final transient после десериализации получает значение по умолчанию.

**22. Cloneable**
Маркерный интерфейс без методов, разрешает Object.clone(). Клонирование по умолчанию поверхностное, конструктор не вызывается. Вместо clone() обычно лучше конструктор копирования.

**23. AutoCloseable**
Один метод close(). Позволяет использовать объект в try-with-resources: ресурс закрывается автоматически в обратном порядке, ошибки из close() сохраняются как suppressed.

**24. Functional interface**
Интерфейс ровно с одним абстрактным методом. В отличие от обычного, его можно реализовать лямбдой или ссылкой на метод. @FunctionalInterface проверяет это при компиляции.

**25. Atomic types**
Классы AtomicInteger, AtomicLong, AtomicReference и др. Дают атомарные потокобезопасные операции без блокировок (через CAS). Нужны для счётчиков и флагов, потому что `count++` не атомарен.

**26. Happens-before и volatile**
Happens-before - правило модели памяти: изменения из действия A гарантированно видны в действии B. volatile гарантирует видимость изменений между потоками и запрещает перестановку операций, но не делает атомарными составные операции (`count++`).

**27. Heap и Stack, где хранятся примитивы**
Stack у каждого потока свой, хранит фреймы методов: локальные переменные и ссылки, очищается при выходе из метода. Heap общий, хранит объекты, очищается сборщиком мусора. Локальные примитивы лежат в стеке, примитивные поля объектов - в куче.

**28. Когда резервируется память и зачем разделение**
Стек создаётся вместе с потоком, фрейм выделяется при вызове метода и удаляется при выходе. Куча резервируется при старте JVM, память под объект выделяется при new. Разделение нужно из-за разного времени жизни данных: стек быстрый и не требует синхронизации, а GC нужен только для кучи.

**29. Принципы и области памяти Garbage Collector**
Объект - мусор, если до него нельзя дойти по ссылкам от GC Roots. Куча делится на Young Generation (Eden, Survivor S0/S1) и Old Generation, метаданные классов хранятся в Metaspace. Minor GC чистит молодое поколение, Full GC - всю кучу.

**30. Reference counting и Tracing**
Reference counting считает ссылки на объект и удаляет его при нуле, но не видит циклические ссылки. Tracing обходит граф объектов от GC Roots и удаляет всё недостижимое. В JVM используется Tracing.

**31. Autoboxing**
Автоматическое преобразование примитива в обёртку и обратно: компилятор подставляет Integer.valueOf() и intValue(). Подводные камни: кэш Integer от -128 до 127 (`==` для 128 даёт false), NullPointerException при распаковке null.

**32. Сериализация**
Класс реализует Serializable, объект пишется через ObjectOutputStream и читается через ObjectInputStream, версия задаётся serialVersionUID. Встречается в репликации сессий Tomcat, RMI, распределённых кэшах.

**33. WeakReference и SoftReference**
WeakReference удаляется при первой же сборке мусора (WeakHashMap). SoftReference удаляется только при нехватке памяти (кэши).

**34. Generics**
Параметризация классов и методов типами (`List<String>`). Дают проверку типов при компиляции вместо ClassCastException во время работы и избавляют от приведений типов.

**35. PECS**
Producer Extends, Consumer Super: если из коллекции читаем - `? extends T`, если пишем - `? super T`.
```java
double sum(List<? extends Number> numbers)
void fill(List<? super Integer> target)
```

**36. Зачем immutable объекты на практике**
Потокобезопасность без синхронизации, надёжные ключи HashMap, безопасное кэширование, не нужны защитные копии. Примеры: деньги, даты, DTO, конфигурация.

**37. Maven, Ant, Gradle**
Автоматизируют сборку: компиляция, тесты, упаковка в jar/war и скачивание зависимостей. Ant - ручное описание шагов, Maven - соглашения и pom.xml, Gradle - гибкие скрипты и быстрая инкрементальная сборка.

**38. Spring Core, IoC и DI**
Spring Core - основа Spring с IoC-контейнером, который создаёт объекты (бины) и связывает их. IoC - управление созданием объектов передаётся фреймворку. DI - объект получает зависимости извне (через конструктор), а не создаёт их через new.

**39. Как работает @Transactional**
Spring оборачивает бин в прокси. Прокси перед вызовом метода открывает транзакцию, после него делает commit, а при RuntimeException - rollback. Поэтому вызов метода изнутри того же класса и private методы транзакцию не получают.

## Базы данных, библиотеки и стандарты

**40. Реляционные и нереляционные БД**
Реляционные - таблицы со строгой схемой, связи через ключи, SQL, ACID (PostgreSQL, MySQL). Нереляционные - гибкая схема, документы, ключ-значение, графы, легко масштабируются горизонтально (MongoDB, Redis).

**41. one-to-one, one-to-many, many-to-many в таблицах**
One-to-one - внешний ключ с UNIQUE. One-to-many - внешний ключ в таблице на стороне "многие". Many-to-many - отдельная связующая таблица с двумя внешними ключами.

**42. Нормализация**
Устранение дублирования данных разбиением на таблицы (1НФ, 2НФ, 3НФ). Пример из КТ-3: теги вынесены в таблицы tags и task_tags вместо строки "учёба, срочно" в задаче, данные пользователя хранятся в users, а в задаче только user_id.

**43. Виды индексов**
По структуре: B-tree, Hash, GIN, GiST, BRIN. По назначению: уникальный, составной, частичный, по выражению, покрывающий, кластерный и некластерный.

**44. Hibernate, JPA и Hibernate**
Hibernate - ORM-фреймворк, который связывает Java-классы с таблицами и сам генерирует SQL. JPA - спецификация (интерфейсы и аннотации), Hibernate - её реализация.

**45. Каскадность в Hibernate**
Автоматическое применение операции над родителем к связанным сущностям. Задаётся параметром cascade (PERSIST, MERGE, REMOVE, ALL): `@OneToMany(cascade = CascadeType.ALL)`.

**46. Абстрактный entity-класс**
Может. Используется в наследовании сущностей (@Inheritance), запросы по нему возвращают объекты подклассов.

**47. EntityManager**
Главный интерфейс JPA для работы с БД: persist, find, merge, remove, запросы. Управляет контекстом персистентности: кэширует сущности и сам сохраняет их изменения при коммите.

**48. Класс Assert**
В тестах (JUnit) - методы assertEquals, assertTrue, assertNotNull и др. для проверки результата, при неудаче тест падает. В Spring (org.springframework.util.Assert) - проверка аргументов в коде, при нарушении бросает IllegalArgumentException.
